1. HOW WE GOT HERE (history of the branch — important context)
--------------------------------------------------------------------------------
The branch went through several iterations of "how does an out-of-process SDK
worker tool get a per-user secret?" (secret is keyed by workflow.createdBy):

  Iteration 1: Status listener mints an execution token in
               AgentEventListener.onWorkflowStarted, mutates workflow input.
               FAILED: orkes does not persist a status-listener's workflow
               mutations -> token lost before first task ran. (This was the
               original "webhook execution token" bug the branch name refers to.)

  Iteration 2: Compiler injects an AGENTSPAN_MINT_TOKEN system task as the first
               node of every workflow; mints token into workflow.variables.
               (THIS is what an earlier turn of THIS conversation committed —
               that commit is now OBSOLETE; see below.)
               Rejected: visible distracting node in every graph; still a bespoke
               capability token fetched over /api/workers/secrets.

  Iteration 3: Pull-based — worker sends workflowId to /api/workers/secrets,
               server derives owner from createdBy, returns secrets.
               Rejected: still a special endpoint + SDK fetcher in 4 languages.

  Iteration 4 (CURRENT, "Implemented" per design doc): POLL-TIME INJECTION.
               See docs/design/2026-06-25-worker-secret-delivery-design.md
               WorkerSecretPollAdvice (a Spring ResponseBodyAdvice over
               /api/tasks/poll/{type}) resolves per-user secrets server-side and
               injects __resolved_credentials__:{NAME:value} into the TRANSIENT
               poll response (never persisted; persisted task input has NAMES
               only). The SDK reads __resolved_credentials__ and strips it.

2. THE GAP THIS PLAN FIXES
--------------------------------------------------------------------------------
The poll-time injection design (Iteration 4) works ONLY when the worker polls
THROUGH the agentspan server (standalone, or embedded where agentspan owns the
poll path). The design doc §6 explicitly states: "If a different host (e.g.
orkes-conductor) serves the poll, that host must perform the substitution
instead."

In a real orkes-embedded deployment ORKES serves /api/tasks/poll, NOT agentspan.
So WorkerSecretPollAdvice does not (and should not) run. Orkes only resolves
${workflow.secrets.NAME} references that physically appear in TASK INPUT.

Today, SDK worker-tool task inputs carry NO such references — credential NAMES
live only in WorkflowDef metadata (agentspan_tool_credentials /
agentspan_workflow_credentials), which orkes knows nothing about. Therefore, in
embedded mode, SDK worker tools currently get NO secrets. THAT is the gap.

(HTTP/MCP server-side tool headers ALREADY emit ${workflow.secrets.NAME} in
embedded mode via ToolCompiler.rewriteCredentialPlaceholders — so only the SDK
"worker" (Conductor SIMPLE task) path is the gap.)

4. CRITICAL ARCHITECTURE CORRECTION (from Plan agent)
--------------------------------------------------------------------------------
SDK worker tools are NOT built as static WorkflowTask objects (except framework
passthrough). They are dispatched DYNAMICALLY at runtime by a baked-in GraalJS
"enrich" script inside an INLINE task, then a FORK_JOIN_DYNAMIC runs them. The
enrich script builds each tool call's WorkflowTask (incl. inputParameters) live.

=> To stamp __resolved_credentials__ for worker tools, you must edit the JS enrich
   script's `if (t.type === 'SIMPLE')` block, fed by a NEW compile-time
   `workerCredCfg` JSON literal. NOT static task input (except passthrough).

ENUMERATION of SIMPLE-worker-tool build sites:
 DYNAMIC (the real worker-tool path):
  - ToolCompiler.buildEnrichTask(...)        ToolCompiler.java:304
      -> JavaScriptBuilder.enrichToolsScript(...) called at :420
      -> SIMPLE branch in JavaScriptBuilder.java:692-695
  - ToolCompiler.buildEnrichTaskDynamic(...)  ToolCompiler.java:1486  (MCP/API discovery variant)
      -> JavaScriptBuilder.enrichToolsScriptDynamic(...) called at :1564
      -> SIMPLE branch in JavaScriptBuilder.java:1339-1341
    Both reached from every agent shape via buildForkChain (:511) /
    buildForkChainDynamic (:1438). One change per enrich builder covers simple
    agent, compileWithTools, hybrid, approval, MCP/API-discovery, AND multi-agent
    member agents (members compile via AgentCompiler.compile() reusing the fork chain).
 STATIC (no enrich script):
  - AgentCompiler.compileFrameworkPassthrough(...)  AgentCompiler.java:3477-3485
    (Claude-Code passthrough worker; single fwTask SIMPLE; DOES carry credentials.)
 OPTIONAL:
  - AgentCompiler.compilePrefillTasks(...)  AgentCompiler.java:1127-1141
    (prefill tool calls — static SIMPLE; per-tool names via ptc.getToolName()).
 NOT worker tools (internal orchestration — DO NOT stamp): MultiAgentCompiler
  :868 (router), :1203 (handoff check), :1381/:1492 (checkTransfer), :1586
  (process_selection), :2240 (planReader); AgentCompiler:803 (checkTransfer).

CREDENTIAL NAMES per tool: reuse AgentCompiler.collectToolCredentials(config)
 (private static, AgentCompiler.java:3433-3450; encodes per-tool creds from
 tool.getConfig().get("credentials") with AGENT-LEVEL FALLBACK to config creds)
 and collectCredentialUnion(config) (:3453-3466).
 RISK: the enrich builders currently receive only List<ToolConfig> tools, NOT the
 agent-level config.getCredentials(). If you build workerCredCfg solely from
 tool.getConfig().get("credentials") you LOSE the agent-level fallback. MITIGATION:
 make collectToolCredentials package-visible static and PLUMB the precomputed
 Map<String,List<String>> into buildEnrichTask/buildEnrichTaskDynamic from AgentCompiler.
